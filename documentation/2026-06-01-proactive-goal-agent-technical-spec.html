Technical spec

Blurp Proactive Goal Agent

This document defines the backend and agent architecture for Blurp's proactive goal agent. The functional behavior is defined separately in the product behavior document.

Date: 2026-06-01 Status: Draft technical specification Scope: backend and agent architecture

Summary

The system transitions from scheduled reminders to scheduled agent work. The product behavior document defines heartbeats, tasks, and proactive messaging; this spec defines how those behaviors are represented in Convex, agent execution, chat creation, push delivery, and learning storage.

Convex owns the scheduling and persistence layer. V1 heartbeat timing is planned by a daily Convex cron job, then materialized as agentActivations rows scheduled with Convex one-shot scheduled functions. Tasks use the same one-shot scheduling path. The same table also records historical activation execution so Blurp can reason from scheduled times, execution status, created chat threads, push notifications, follow-up tasks, and silent activations.

Scheduling and execution are separate responsibilities: Convex tracks due activations, and the activation executor performs the agent work with the relevant activation, app, and learning context. The executor gives the proactive agent the context and capabilities it needs to carry out the activation according to the agent activation flow, such as, but not limited to, approved tools, future task scheduling, learning updates, and proactive messaging.

Proactive messaging uses the ordinary chat system. When an activation messages Kyle, it creates a new regular chat thread, writes the opening agent message there, and sends a push notification that opens that thread. It does not route new proactive messaging through the existing Check-in section.

Learning is a first-class part of the design. The system needs durable storage and retrieval for what Blurp learns about Kyle, including both the psychological model of Kyle and the model of what kinds of help actually move him toward his goals. The exact storage model is specified in the Agent Learning And Memory section.

The old goal-owned notification system is deprecated rather than deleted. Existing tables, historical rows, proposal shapes, and compatibility code remain available, but scheduled goal notifications no longer fire, and notification proposal tools are removed from the active chat agent tool set. Web Push delivery remains in use for proactive agent messaging.

Scheduling And Activation Records

Scheduling persists future agent activations with timing, briefs, and execution history. This technical surface covers Convex scheduling and app-level activation records.

Concrete Scheduling

Heartbeat scheduling and task scheduling both use the same concrete scheduling path. That shared path turns an intended future activation into an agentActivations row and a Convex one-shot scheduled function.

The shared scheduler receives an activation kind, a concrete scheduledAt timestamp, a source type such as heartbeat planner, ordinary chat, or agent activation, and brief text when present. It creates the app-level activation record, calls Convex ctx.scheduler.runAt, and stores the returned scheduled-function id with the activation.

Reconciliation only changes pending future activations. Activations that have already started or completed remain as history.

Heartbeat Scheduling

Heartbeat scheduling uses one built-in Convex cron job as a daily planner. The cron fires at midnight, reads the current heartbeat schedule configuration, and uses concrete scheduling to create that day's heartbeats.

The heartbeat schedule configuration table stores enabled, dailyHeartbeatUtcMinutes, updatedAt, and updatedBy. dailyHeartbeatUtcMinutes is an array of minute-of-day numbers from 0 to 1439, interpreted in UTC.

The chat agent and proactive agent have access to a heartbeat-schedule management tool. The tool updates the heartbeat schedule configuration and reconciles any pending heartbeats for the rest of the current day.

The tool accepts dailyHeartbeatUtcMinutes, the desired heartbeat cadence as UTC minute-of-day values; effectiveFrom, the first date or timestamp when the new schedule should apply; and enabled, whether heartbeat planning should create heartbeats.

When an agent updates the cadence from Kyle-local intent, the tool call uses UTC minute-of-day values. The agent receives Kyle's current timezone context before making the tool call.

When called, the tool updates the schedule configuration and reconciles pending heartbeats for the rest of the current day through concrete scheduling.

Task Scheduling

Ordinary chats and agent activations create tasks using a scheduled time and brief.

The chat agent and proactive agent have access to a task scheduling tool. The tool creates a future agent activation with a scheduled time and brief through concrete scheduling.

The tool accepts at, an ISO datetime with timezone offset for when the future task should start, and brief, the handoff text written by the current agent for the future activation. Any goal-specific information belongs inside the brief text.

When called, the tool returns the created activation id and scheduled time.

Agent Activation Records

The agentActivations table stores the minimum state needed to schedule, execute, and reconcile proactive agent activations.

Required V1 fields are kind, status, scheduledAt, scheduledFunctionId, brief, and sourceType.

  • kind distinguishes heartbeats from tasks.
  • status lets scheduling code identify pending activations and avoid mutating activations that already started or finished.
  • scheduledAt stores the concrete UTC timestamp used for scheduling and ordering future activations.
  • scheduledFunctionId links a pending activation to the Convex scheduled function that can be canceled or replaced.
  • brief stores the text passed to the future agent activation; heartbeats may leave it empty.
  • sourceType records whether the activation came from the heartbeat planner, an ordinary chat, or another agent activation.

Richer tracking fields such as source thread, parent activation, created thread, push metadata, response tracking, and error details are deferred until the product needs them.
