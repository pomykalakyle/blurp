# Goal Check-In Chat — Functional Spec

Date: 2026-05-17
Status: Draft

---

## 1. Summary

A second kind of chat thread alongside the regular [Claude Chat](2026-05-17-claude-chat-functional-review.md). Where the regular chat is open-ended and user-initiated (the user sends the first message), a **goal check-in chat** is a chat focused on reviewing the status of the user's goals where **the assistant speaks first** — opening with a direct status question about a specific goal.

In this v1, the only way a check-in chat is created is manually, from a new **Check-in** section in the left sidebar. The future [goal notifications system](2026-05-17-goal-notifications-spec.md) will also create check-in chats automatically, with additional structure (a snapshotted list of overdue goals it's specifically about). That additional structure lives in the notifications spec, not here — this doc only covers the manual chat type.

---

## 2. What makes it different from a regular chat

A goal check-in chat reuses most of the regular chat surface — same streaming, same propose-cards, same propose-tools. The differences are:

- **Assistant speaks first.** The first message in the thread is from the assistant.
- **Focus on goal status.** The chat exists to review where the user is on his goals. The assistant is primed to start with goals whose end date is recent (just-ended or about to end) and then follow the user wherever the conversation goes.
- **Different system prompt.** A small variant that explains the check-in context.
- **Two-pane desktop layout.** On desktop only, the check-in chat renders the full goals view alongside the chat (see §6).

No persisted "resolution" state, no separate per-goal "addressed" flag. Whether a goal was discussed is just the conversational record. What actually changes anything is the goal mutation the user accepts during the chat — mark done, mark slipped, extend deadline. The chat itself doesn't carry an open/closed state.

---

## 3. Entry point

There is one entry point: a new **Check-in** section in the left sidebar, added alongside the existing Goals, Chat, and Narrative sections. The section shows a list of check-in chats (sorted by most-recent activity) and a "+ New check-in" button at the top of the list — same shape as the Chat section's list.

Regular chats stay in the Chat section. Check-in chats never appear in the Chat section's list, and regular chats never appear in the Check-in section's list. The section itself is the marker — no per-row icon or prefix needed.

Clicking "+ New check-in" creates a new chat and navigates the user into it immediately. The assistant's opening message streams in over the next few seconds.

(When the notifications system is built later, it will also create chats in this list — see [notifications spec](2026-05-17-goal-notifications-spec.md). The Check-in section will display those alongside manually-created ones identically. the user interacts with both the same way.)

---

## 4. Seeded opening

When a check-in chat is created, the assistant's first message is generated by the model on the spot. The model has the user's full goals and LTGs picture in context (same as regular chat) and is instructed to open with a direct status question — leading with goals whose end date is most recent past or imminent.

**Tone is direct, not warm.** No "hey, checking in," no preamble. The assistant names a goal and asks for its status. Examples of the kind of opening we want:

> "*Workout 3x this week* just wrapped up — did you get it done?"

> "*Ship the prototype* ended yesterday. Status?"

> "*Workout 3x* ended yesterday and *Read 30 min daily* wraps up tomorrow. Did you finish *Workout 3x*?"

The model picks which goal(s) to lead with based on recency — not a fixed list, just whatever is most timely. From there it's a normal conversation.

---

## 5. How a check-in plays out

The assistant's job during a check-in:

1. Review the user's goals, starting with recently-due or imminently-due ones.
2. For each goal the user answers on, propose the appropriate goal mutation via existing tools — `propose_toggle_goal_state` to mark done or slipped, `propose_edit_goal` to extend a deadline, etc.
3. Follow the user's lead. If the user wants to talk about a specific goal, an LTG, or something else, go there.

The chat isn't trying to "complete" a fixed checklist. It's a goal-status conversation. When the user's done talking, he stops; the chat sits in the Check-in list and can be returned to or simply left alone.

**the user can also mutate goals directly via the right-pane Goals view** during a check-in (clicking complete on a goal card, editing, etc.). Those mutations are real goal-state changes and will be reflected in the model's context on its next turn — so if the user pre-empts a question by handling a goal in the right pane, the model can move on. The model isn't tracking "did I cover this in chat"; it's just looking at current goal state.

**Stale chats are fine.** A check-in that the user stopped replying to just sits in the list. It doesn't auto-close, doesn't nag, doesn't disappear.

## 6. Layout

### 6.1 Desktop

When a check-in chat is active, the main content area splits into two panes. The chat occupies the left pane (same UX as a regular chat). The right pane renders **all of the user's goals** by reusing the existing Goals section view — same components, same interactions (add, edit, complete, archive).

Because Convex is reactive, any data change the assistant proposes and the user accepts during the chat — and any change the user makes directly via the right pane — updates the other side automatically. The same code powers the Goals section and this right pane, so they always stay consistent.

Layout, left-to-right: section sidebar (with the Check-in section's chat list visible) | chat | goals view.

### 6.2 Mobile (phone)

The right-pane goals view is **not shown** on phone. A check-in chat looks identical to a regular chat on mobile — full-screen chat, no goals panel. The smaller screen doesn't fit side-by-side, and we'd rather keep mobile clean. the user can navigate to the Goals section directly if he wants to see goals on mobile.

---

## 7. System prompt

A small variant on the base system prompt. v1 is intentionally basic — adds a few sentences explaining the check-in context:

- You are starting a goal check-in with the user.
- Open with a direct status question about one of his goals — lead with whichever has the most recent past end date or the most imminent upcoming end date. No "hey checking in" preamble.
- Use propose-tools to record what the user tells you (complete, slipped, extended deadline, etc.).
- Follow the user where the conversation goes. Don't force a checklist.

The full goals and LTGs context is injected the same way as in regular chat. the user will iterate on this prompt once the chat is interactable.

---

## 8. Check-in list and titling

The Check-in sidebar section's list mirrors the Chat section's list visually: each row shows the title, a short preview from the most recent message, and a relative timestamp. Auto-titling applies the same way (3–6 words after the first user→assistant exchange). The seeded opening counts as the assistant's first turn, so titling can fire as soon as the user replies.

Sorting, rename behavior, and multi-device sync all match the Chat section.

---

## 9. Data model and agent implications

Conceptually, the chat thread gains one piece of metadata:

- **`kind`** — `"regular" | "goal_check_in"`. Distinguishes the chat for purposes of which sidebar section it appears in, whether to seed an opening message, whether to use the check-in system-prompt variant, and (on desktop) whether to render the right-pane goals view.

Threads themselves are owned by the `@convex-dev/agent` component, so this metadata lives in a thin sidecar table keyed by `threadId`. Implementation detail; resolved during build.

(Notification-triggered check-ins will need an additional `scopeGoalIds` field. That's covered in the notifications spec, not here.)

**No new tools.** Existing `propose_toggle_goal_state`, `propose_edit_goal`, etc. cover everything a check-in produces.

**One agent, conditional behavior.** The existing `BlurpChat` agent stays as the single agent. At runtime, when invoked on a thread with `kind === "goal_check_in"`, the system prompt is amended with the check-in instructions (see §7). The tool list is unchanged. No separate `CheckInAgent` is defined.

---

## 10. Out of scope for v1

- Programmatic (notification-triggered) check-in chats with snapshotted scope. Covered in the notifications spec.
- LTG-scoped check-ins ("check in on everything under LTG X").
- Mobile goals panel.
- Goals panel in regular (non-check-in) chats.
- Mixing check-in chats and regular chats into a single sidebar list.
