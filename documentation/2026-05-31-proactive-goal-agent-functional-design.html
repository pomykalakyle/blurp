Product behavior

Blurp Proactive Goal Agent

Blurp should stop acting like a passive goal ledger. It should become an active thinking partner that notices drift, finds useful openings, follows up when timing matters, and learns what actually helps Kyle move toward the goals he cares about.

Date: 2026-05-31 Status: Product direction draft Scope: user-facing behavior

Product Direction

Active Goal-Seeking

Blurp should act like a second brain focused on helping Kyle reach his goals. It should carry some of the noticing, remembering, researching, following up, and strategy adjustment that Kyle would otherwise have to do alone.

The product should keep thinking about how to help even when Kyle is not actively driving the conversation. Blurp is an active participant in goal progress; when it reaches out, it should feel like something has been paying attention on Kyle's behalf.

Model Shift

This direction replaces the current notification model. Blurp moves away from goal-owned notification schedules and toward recurring background thinking where the agent decides how to help from the current situation.

Functionality being removed

  • Per-goal notification schedules.
  • Required post-deadline pings for every new goal.
  • Reminder/check-in behavior driven mechanically by a deadline.
  • Assistant behavior centered on choosing notification timings for new goals.

Functionality not being removed

  • Long-term goals and short-term goals remain part of the product.
  • Goal dates, outcomes, notes, and changes remain part of the goal landscape Blurp reasons from.
  • Kyle can still use goals to name what he is trying to move toward.

Replacement behavior

  • Heartbeat runs and contextual runs give Blurp recurring chances to think and decide what, if anything, to do.
  • The agent learns what helps Kyle move toward his goals.
  • Blurp builds a psychological model of Kyle oriented around helping him move toward the goals he cares about.
  • Proactive contact appears as a normal chat thread and phone ping.

Run Scheduling

Heartbeat Runs

Blurp starts with three regular agent runs each day. These are scheduled chances for the agent to think, independent of any individual goal deadline.

Run time Cadence note
8:30am Eastern Chosen because Kyle is often at the dog park and free enough to read something.
1:30pm Eastern Default daily run slot.
6:30pm Eastern Default daily run slot before Kyle's sleep window.
These times are defaults. Blurp can adjust the schedule as it learns when agent runs are useful.

Contextual Runs

Blurp can schedule runs outside the daily heartbeat cadence. These runs have a specific time and a short piece of context explaining why the agent is running then.

The context can come from conversation, goals, outside events, or the agent's own prior work. It gives Blurp the right starting point when that run begins.

  • Run after Kyle expects to be back from a date, with the date as context.
  • Run near the time of a local-government event, with the event link or description as context.
  • Run before an opportunity window closes, with the relevant goal and deadline as context.
  • Run to revisit an event schedule Blurp has been tracking, with the reason it might matter to Kyle as context.

Creating Contextual Runs

Blurp has a run-scheduling capability available from ordinary chats and from agent runs. To create a contextual run, the agent gives the system a time and a text context for why that future run should exist.

The scheduling capability includes a context field. The agent writes the handoff text for the future run there, so the future agent knows what situation it is being asked to continue.

Agent Run Flow

This section is organized as the functional flow of an agent run. Read 3.1 through 3.4 as the product-level sequence Blurp follows during a run, while leaving the internal execution model to the technical design.

Start From Run Context

Each run starts from the reason it exists. A heartbeat run has broad responsibility for Kyle's current goal landscape. A contextual run starts from its attached context: an event, date, deadline, opportunity window, prior thought, or other scheduled reason.

The run's job is to improve the odds of progress from that starting point.

Learn From Recent Activity

Run scope

Heartbeat runs review recent activity that is ready to become durable learning: new or changed chats, goal outcomes, narrative entries, and other relevant app context.

Contextual runs stay focused on their attached context. They can update learning related to that context, while broad review of unrelated activity belongs to heartbeat runs.

What Blurp learns

Blurp builds a psychological model of Kyle so it can understand him well enough to help. This includes preferences, motivation, friction, timing, tone, recurring patterns, and the situations where Kyle tends to engage, avoid, stall, or follow through.

Blurp also learns what works. It tracks which kinds of help actually move Kyle toward his goals: useful timing, effective follow-up, helpful research, good questions, bad interruptions, successful reframes, and strategies that made progress more likely.

These two forms of learning inform each other. The psychological model helps Blurp choose better strategies, and the results of those strategies update what Blurp understands about Kyle. Both are oriented around helping Kyle move toward the goals he cares about.

Natural-language steering is part of recent activity. When Kyle corrects Blurp, asks it to slow down, tells it to stop pursuing a topic, replies later, stays silent, shows interest, says a message was useful or annoying, or changes how he wants the agent to behave, Blurp carries that forward into future runs, contact decisions, and its internal model of Kyle.

When a goal outcome or follow-through pattern is informative, Blurp can treat it as a retrospective: understand what happened, update its strategy, and carry the learning into future runs.

Pursue Goal Progress

During this phase, Blurp works through what would make progress more likely. This is the agentic work session inside the run: Blurp has a purpose and context, but its exact path emerges from what it discovers while working.

Blurp can reason, revise its strategy, and continue exploring as the situation develops. It also has tools available during this phase, including capabilities such as researching outside information, inspecting available app context, scheduling another run, or using other useful tools added over time.

The work can be iterative. Blurp might research an event, learn that it is more relevant than expected, then decide to involve Kyle. Or it might investigate an opportunity and carry what it learned forward for a better moment.

Contact Kyle When Useful

If a run needs Kyle's attention, Blurp creates a normal chat thread in the existing chat list and sends a phone notification that opens it. The opening message should fit what the run found useful to say in that moment, such as a question, finding, proposed direction, follow-up, or another useful form of contact.

Contact is one possible action during a run. Blurp reaches out when, based on the reason for the run, what it found while working, Kyle's goals, and what it has learned about how to help him, involving Kyle seems likely to help him move toward a goal, clarify something the agent cannot resolve alone, or preserve useful momentum. A run can also save learning, schedule another run, continue working, or let the thread of work rest.

Blurp's contact judgment improves from Kyle's reactions. If Kyle responds better at certain times, ignores certain kinds of outreach, or says a kind of contact is annoying, future runs should use that learning when deciding whether and how to contact him.

The thread behaves like any other chat. Kyle can reply, ignore it, accept proposals, dismiss proposals, or steer it somewhere else in natural language, and Blurp can learn from what happens afterward.

Out of Scope

The exact model for storing Blurp's learnings about Kyle belongs in a separate technical design. That document should cover the memory system, chat-history search, psychological-model storage, update mechanics, and retrieval behavior that support the product behavior described here.

The technical design should also decide how the learning phase and goal-progress phase are orchestrated internally, including whether they run as one agent, separate agents, or another execution structure.
