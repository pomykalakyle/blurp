Blurp × Hermes integration options

System design sketches for keeping Blurp as the chat surface while Hermes runs on the user’s computer.

These diagrams are grounded in the current Blurp codebase: Convex owns thread/message state, the React app sends prompts through api.chat.public.sendMessage, and web push currently deep-links users back into the PWA rather than delivering full off-app chat.

Option A — Convex calls Hermes directly over HTTP

Best if you want Blurp to remain the single frontend and are comfortable exposing a secured Hermes API endpoint from the home computer.

Best product fit

How messages go in

  • Phone sends prompt through the existing Blurp chat UI.
  • Convex action becomes the integration point.
  • Convex forwards prompt + context to Hermes HTTP API.

How replies come back

  • Hermes returns text (or structured output) in the same HTTP call.
  • Convex writes the assistant turn into the existing thread.
  • Blurp UI renders it using the current thread/message model.

Main tradeoff

  • Clean architecture and best UX fit.
  • Requires a secure public or semi-public route to the Mac.
  • Need auth, availability, and timeout handling.

Option B — Mac worker polls Convex and runs Hermes locally

Best if you want Hermes to stay private on the home computer and do not want Convex calling into your machine over the internet.

Safest networking model

How messages go in

  • Blurp stores user messages immediately in Convex.
  • A pending Hermes job row is created for each turn.
  • A worker process on the Mac picks jobs up.

How replies come back

  • Worker runs Hermes locally with full machine access.
  • Worker writes assistant output into Convex.
  • Phone receives the update through the normal Blurp realtime path.

Main tradeoff

  • Strong security posture; no public Hermes endpoint.
  • More moving parts: queueing, retries, worker health.
  • Slightly less immediate than pure request/response.

Option C — Blurp talks directly to Hermes from the browser

Conceptually simple, but usually the weakest option because it pushes networking, auth, and uptime complexity into the mobile client.

Least recommended

How messages go in

  • Browser sends prompts directly to Hermes.
  • Convex is no longer the main ingress path.
  • The phone now depends on being able to reach your Mac.

How replies come back

  • Hermes responds directly to the phone over HTTP/SSE.
  • Optional: mirror the transcript back into Convex afterward.
  • State split becomes awkward if persistence lags.

Main tradeoff

  • Feels simple at first glance.
  • Usually worst for auth, resilience, and product coherence.
  • Not a great match for how Blurp is currently structured.

Option D — Hybrid: Blurp keeps normal chat local, Hermes handles only special threads

Use the current Blurp agent for lightweight/fast chats, but route selected thread types like check-ins, planning, or “assistant mode” to Hermes.

Incremental migration path

How messages go in

  • All user messages still enter through Blurp.
  • Convex decides which backend should handle the thread.
  • Check-ins or “Hermes mode” could be routed specially.

How replies come back

  • Both backends write into the same thread abstraction.
  • UI does not need separate screens.
  • You can migrate gradually instead of replacing everything at once.

Main tradeoff

  • Great migration strategy.
  • More conceptual complexity because two agents coexist.
  • Good if you want to learn before fully committing.
